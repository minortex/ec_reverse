# 充电上下限寄存器固件消费情况调查（2026-07-25）

## 1. 结论摘要

根据真机实测和对主 EC 固件二进制（`GXxHXxx_21.200` 对应的 `main-bank0.bin` 和 `main-bank1.bin`）的扫描，得出以下结论：

1. **充电上限 `EC[0x07B9]`（`battery_charge_limit_high`）拥有完整的固件消费逻辑**。主 EC 会在电池周期任务中周期性读取当前 SOC，并与 `EC[0x07B9]` 的低 7 位（阈值百分比）做比较：
   - 达到上限时，置位 `EC[0x07B9]` 的 bit 7 触发停充。
   - 跌破上限时，清除 bit 7 以恢复充电。
   - 主机工具 `mech-forza-control` 的 `setc` 子命令保留 bit 7 并写回低 7 位的策略完全契合固件的位掩码定义，因此上限限制能够立刻生效。

2. **充电下限 `EC[0x07D0]`（`battery_charge_limit_low`）在主 EC 固件中没有任何消费者**。
   - 经对 `main-bank0.bin` 和 `main-bank1.bin` 原始 opcode 字节流的深度扫描，发现 `EC[0x07D0]` 在整个程序空间中**从未被读取或访问**（`MOV DPTR, #0x07D0` 命中数为 0）。
   - 对独立加载 `mov DPH, #0x07; mov DPL, #0xD0` 以及表驱动字节等可能形式的核对同样为零命中。
   - 官方提供的 GCU Service 及其寄存器常量表仅在主机侧映射了该地址，但固件层并未实现任何基于下限阈值重新启动充电的控制回路。因此，在主机端写入下限不会对硬件充电行为产生任何影响。

## 2. 充电上限 `0x07B9` 的固件消费链分析

在 `main-bank1.bin`（以及公共区）中存在 9 处 `MOV DPTR, #0x07B9`（opcode `90 07 B9`）的硬编码引用。其核心生命周期与控制逻辑如下：

### 2.1 阈值保存与暂存器合并
在 `bank1` 文件偏移 `0xd655` 一带，EC 从未命名暂存器 `0x087F` 复制用户设定的百分比，并合并当前 bit 7 的停充标记写入 `0x07B9`：
```text
90 08 7F    MOV DPTR, #0x087F
E0          MOVX A, @DPTR
54 7F       ANL A, #0x7F        ; 保留用户输入的 0-100 阈值百分比
FE          MOV R6, A
EF          MOV A, R7           ; 提取当前计算出的 bit 7 状态
4E          ORL A, R6           ; 将 bit 7 状态与低 7 位合并
90 07 B9    MOV DPTR, #0x07B9
F0          MOVX @DPTR, A
```

### 2.2 上限触发与解除的决策段
在 `bank1` 文件偏移 `0xd706` 起的代码段中，EC 读取实时容量百分比 `EC[0x04AB]`，与上限阈值进行比较，控制 bit 7 的置位与清零。

原始机器码与反汇编解析：
```nasm
; 文件偏移 0xd729 起：读取 RSOC 并做减法
d729: 90 04 AB    MOV DPTR, #0x04AB    ; 读取当前 Relative State of Charge
d72c: E0          MOVX A, @DPTR
d72d: C3          CLR C
d72e: 9B          SUBB A, R3           ; R3 存放 0x07B9 的低 7 位阈值

; 决策分支
d72f: 90 07 B9    MOV DPTR, #0x07B9
d732: E0          MOVX A, @DPTR
d733: 40 09       JC +0x09             ; 若 RSOC < 阈值，借位 C=1，跳转至清 bit 7 路径 (0xd73a)

; --- 命中上限：置位 bit 7 (停充) ---
d735: 44 80       ORL A, #0x80         ; 置位 bit 7
d737: F0          MOVX @DPTR, A
d738: 80 07       SJMP +0x07           ; 跳转至汇合处

; --- 低于上限：清除 bit 7 (允许充电) ---
d73a: 90 07 B9    MOV DPTR, #0x07B9    ; 目标地址 0xd73a 由前面的 JC/JZ 等跳转汇合而来
d73d: E0          MOVX A, @DPTR
d73e: 54 7F       ANL A, #0x7F         ; 清除 bit 7
d740: F0          MOVX @DPTR, A
```
该决策回路表明，上限阈值直接作为 `battery_rsoc` 的比较目标，且 bit 7 是决定底层充电控制器的直接关断门禁（Stop Charge Bit）。

## 3. 充电下限 `0x07D0` 的完整排查记录

为了确认 `0x07D0` 是否以任何隐式或变形形式在固件中存在，我们对主 EC 的程序切片（`main-bank0.bin` 和 `main-bank1.bin`）进行了全局字节特征排查：

### 3.1 DPTR 寻址排查
在 8051 架构中，外设 and XRAM 寻址最常用 `MOV DPTR, #imm16`，对应机器码为 `90 high_byte low_byte`。
- 查找 `90 07 D0`：**0 次命中**。
- 作为对比，`90 07 B9`（上限）在两个 bank 中累计有 **11 次**直接命中。

### 3.2 拆分寄存器加载排查
部分编译器优化可能会将 DPTR 拆分为独立的 DPH/DPL 写入，形如：
```nasm
MOV DPH, #0x07  ; 机器码 75 83 07
MOV DPL, #0xD0  ; 机器码 75 82 D0
```
- 查找 `75 83 07`：**0 次**。
- 查找 `75 82 D0` : **0 次**。

### 3.3 数据段与表项特征排查
固件可能存在通过表格寻址或使用特定数组载入变量的可能。我们对全文件包含 `07 D0` 字节序列的所有位置进行了定位：
- `main-bank0.bin` / `main-bank1.bin`：**0 次**。
- `pd-bank0.bin` / `pd-bank1.bin` : 存在 20+ 处 `07 D0` 的片段，但经过上下文复核，全部属于 PD 子固件中 `d0 07 d0 06` 的局部寄存器或传输流数据，与主 EC 充电调度毫无关联。

### 3.4 潜在替身字段的核对
我们进一步核定了寄存器表中定义邻近的几个控制字段：
- `EC[0x0514]`：多次在 `bank1` 中被访问，但其作用是将底层计算出的阻抗/容量等 publish 到公开寄存器 `EC[0x04AB]`，其逻辑并不是下限阈值。
- `EC[0x0A47]`：上限持久化配置值，用于跨 AC/电池会话恢复上限设定。
- `EC[0x0704:0x0705]`（`battery_trip_point`）：ACPI BTP 动态容量跳变警告点，触发 ACPI SCI 中断，用于操作系统电量通知，不参与控制充电器回路的启停。

**排查结论**：在主程序中，没有任何字节在消费或参考 `EC[0x07D0]`。

## 4. 可行解决方案探讨

由于下限不生效的本质原因是**固件缺失消费逻辑**，可以采用以下几种方案进行修正：

### 方案 A：主机端守护进程模拟（零固件风险，推荐）
该方案完全不需要修改 EC 固件，利用已证实有效的 `0x07B9` 限制链路。
- **实现机制**：
  在主机端运行一个轻量级守护循环（可集成至 `mech-forza-control`），周期性读取实时 `battery_rsoc`：
  - 当 SOC 跌破设定下限（例如 40%）时，主动将 `0x07B9` 的限制值覆盖写入 `100`（或 `0`，表示默认不限）。这会强制清除 `0x07B9` 的 bit 7，使 EC 重新开启充电。
  - 当 SOC 重新充至设定上限（例如 80%）时，重新将 `0x07B9` 写回原设定的限制值（如 `80`），让 EC 的硬编码决策链自动接管停充。
- **优点**：无需刷写固件，安全性极高，逻辑直观。

### 方案 B：ACPI 协同路径模拟（低风险，需要 ACPI 支持）
- **实现机制**：
  配置 ACPI 电池剩余容量警告点（BTP0，即写 `0x0704` 字段）。当电量下降到该点时，EC 会产生 `0x89` 查询中断。OS 侧的驱动或服务接收该 ACPI 通知后，调用 ACPI 方法将 `0x07B9` 恢复至默认充电状态。
- **优点**：利用了固件既有的 ACPI SCI 事件，但依赖不同操作系统的 ACPI 驱动支持，实现链条较长，排查和维护成本较高。

### 方案 C：修补固件（高风险，需验证）
- **实现机制**：
  在 `bank1` 中比较 SOC 与上限的附近分支中，手动插桩/修补代码：
  - 读入 `EC[0x07D0] & 0x7F`（如果将 0x07D0 用作用户自定义下限）。
  - 将 `battery_rsoc` 与该值进行比较。
  - 若 `rsoc < down_limit`，强制执行 `7B9 &= 0x7F` 并写回以重新激活充电。
- **难点**：
  IT5571 中代码空间十分紧凑，需要找到不破坏对齐和 bank 校验和的空闲 code cave。由于涉及修改实际控制充电电流/电压的核心状态机，一旦跳转逻辑或栈指针出现偏差，极易引发充电器故障或死锁。

## 6. 官方 GCU Service 代码对比核对

通过解包 `/home/texsd/codes/mech-forza-control/ref/GCUService_decompiled/` 中的官方控制中心服务源码，定位到在 `GCUService.MySystem.BatteryProtection2` 类中，官方确实完整保留了充电上限和下限的定义和逻辑：

### 6.1 寄存器常量定义 (ECSpec.cs)
官方通过以下十进制常数寻址 EC：
- `ADDR_BATTERY_CHARGE_LIMIT_UP = 1977` （即十六进制 `0x07B9`）
- `ADDR_BATTERY_CHARGE_LIMIT_DOWN = 2000` （即十六进制 `0x07D0`）

### 6.2 GCU 写入与读取逻辑 (BatteryProtection2.cs)
```csharp
private void SetBatteryChargingLimit_Up(int limit)
{
    byte b = 0;
    byte b2 = 128;
    this.EcCtrl.Read(base.GetType().Name, 1977, ref b);
    byte b3;
    if (limit == 100) {
        b3 = b & b2;
    } else {
        b3 = (byte)((int)(b & b2) + limit);
    }
    this.EcCtrl.Write(base.GetType().Name, 1977, b3);
}

private void SetBatteryChargingLimit_Down(int limit)
{
    byte b = 0;
    byte b2 = 128;
    this.EcCtrl.Read(base.GetType().Name, 2000, ref b);
    if (limit >= 1 && limit <= 95) {
        byte b3 = (byte)((int)(b & b2) + limit);
        this.EcCtrl.Write(base.GetType().Name, 2000, b3);
    }
}
```

- **解析**：
  GCU 侧对于 `2000`（`0x07D0`，下限）的位操作与 `1977`（`0x07B9`，上限）基本对称，都会保留 bit 7 并写回低 7 位作为阈值百分比。
  同时，这些设定值还会通过 `NvramVariable.SetFwVars("ChargeMinimumLimit", ...)` 存入 BIOS NVRAM 中以求持久化。

这进一步确证了：
1. **寄存器地址与位偏移的正确性**：主机端对于 `0x07D0` 的写操作目标和合并方法是完全符合官方协议设计的。
2. **失效的核心所在**：由于 GCU 是通用的控制台框架，对所有符合电池保护协议的平台暴露出该接口；但由于当前 EC 固件（`GXxHXxx` 系列）中直接剔除了对 `0x07D0` 的读取/消费代码（`90 07 D0` 命中数为 0），导致写入 `2000` 后只能成为“留在内存里的摆设”，EC 无法做出任何实质的启充响应。

## 7. 充电控制状态机（Charge Control State Machine）闭环逻辑

为了搞清上限 `0x07B9` 触发 bit 7 后，是如何最终导致物理充电芯片（Charger IC）停止充电的，我们对 `0x07B9` 引用后的控制流和状态机决策链进行了追踪。

其闭环控制链可被清晰划分为以下四个物理阶段：

### 阶段 1：判定与缓存状态字 `EC[0x0432]`
定时评估任务（位于 `bank1:0xB08F` 附近）会周期性通过 `LCALL 0xC099` 提取 `EC[0x07B9] & 0x80` 的状态。
- **触发停充**：当 `bit 7 == 1`（已达到设定百分比上限）时，状态机将缓存状态字 `EC[0x0432]` 写入 **`2`**：
  ```nasm
  B098: LCALL 0xC099        ; 返回 ACC.7 = bit 7
  B09B: JNZ +0x05 (B0A2)    ; 若 bit 7 = 1，跳到 B0A2
  ...
  B0A2: MOV DPTR, #0x0432
  B0A5: MOV A, #0x02
  B0A7: MOVX @DPTR, A       ; 写入 2
  ```
- **解除停充**：若 bit 7 且其它安全报警位（如 `0x0984.bit 3`）全为 0，则将 `EC[0x0432]` 写入 **`0`**（CLR A）。

### 阶段 2：发布至 `EC[0x0574]` 并判定分支
在 `bank1:0xBA4A` 附近的主决策线上，EC 周期性地把缓存的 `EC[0x0432]` 拷贝到最终发布区 `EC[0x0574]`。随后，控制流根据 `EC[0x0574]` 做出如下分支调度：
- **正常限制充电分支**：若不需要停充，调度到 `0xBA13` 物理出口。
- **关断停充/零电流分支**：若 `EC[0x0574] != 0`，调度到 `0xBA27` 物理出口。

### 阶段 3：装载任务命令字 `EC[0x0850]`
不论走哪一条分支，都会通过 fixed common 跳转 thunk `0x165a` 指向 `bank2:0x9D9F` 来装载底层任务命令字：
- **正常充电**：`R7 = 0x06`，执行 `MOVX @0x0850, A`，使命令字为 `0x06`。
- **限制停充**：`R7 = 0x07`，执行 `MOVX @0x0850, A`，使命令字为 `0x07`。
然后，底层通过 `LJMP 0x1C6C` 切换回 `bank1:0x9DB7` 接管硬件消费。

### 阶段 4：执行层硬件 SMBus 封锁电流
`bank1:0x9DB7` 在读取 `EC[0x0850]`（此时已载入 R5 寄存器）后，调用 `LCALL 0x8686` 分发中枢：
```nasm
868C: MOV DPTR, #0x06E6
868F: MOVX A, @DPTR
8690: CJNE R5, #0x07, +0x03    ; 判断命令号是否为 0x07 (停充命令)
8693: LJMP 0x8015             ; 若为 0x07，执行 LJMP 0x8015
```
落入 `0x8015` 动作块后，底层命令 worker 执行 `LCALL 0x8259` 检测充电总线及防抖。最后将 SMBus 的 `ChargingCurrent`（寄存器 `0x14`）**直接清零**写回物理充电器 IC，彻底封锁充电电流。

通过这一条多级传递与分发的“缓存(0x0432) -> 发布(0x0574) -> 命令(0x0850) -> 动作分发(0x8686) -> 封锁零电流(0x8015)”链路，上限 bit 7 得以在硬件层级实现物理充电断开。
